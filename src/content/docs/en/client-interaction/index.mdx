## The server is not always the one with the answer

Most of MCP flows one way: the client asks, the server answers. `tools/list`, `tools/call`, `resources/read` — request in, result out. But a real tool sometimes hits a wall halfway through:

- **It needs a human decision.** "Book the table for 4 or 6 people?" "Which region should I deploy to?" Only the user can say.
- **It needs a secret it must not see in the clear.** An API key for a third-party service, a payment authorization, an OAuth consent.
- **It will take longer than one HTTP request can politely stay open.** A CI pipeline, a bulk import, a job that waits on an approval.

In every one of these the *server* needs something from the *client* — but MCP is a stateless, client-driven protocol. That single design decision shapes everything in this module.

## The constraint: no server-initiated requests

In the 2026-07-28 revision, MCP is stateless: every request carries everything the server needs in its `_meta`, and a server must not infer anything from a previous request on the same connection. A consequence that surprises people coming from legacy (2025-11-25 and earlier): **the server can no longer send its own JSON-RPC requests to the client**. There is no open channel on which `elicitation/create` or `sampling/createMessage` could travel upstream.

So instead of *sending a request*, the server *returns a result that asks for input*. The client gathers it and **retries the original request** with the answers attached. That is the Multi Round-Trip Requests pattern (MRTR), and it is the backbone of everything below.

## Two kinds of "wait"

It helps to separate the cases by *who* the server is waiting on:

- **Waiting on the user** — elicitation. The answer comes from a person, through the client's UI. Under MRTR the server does not wait at all: it returns, and the retry brings the answer.
- **Waiting on time** — a long-running operation. The connection is the fragile part here. Progress notifications keep a single request alive and honest; the Tasks extension turns the work into a durable handle you can poll after reconnecting.

Both keep the server free of per-connection state. The state either travels with the request (`requestState`) or is an explicit identifier (`taskId`) the client passes on every call.

## What was retired

Three client features were deprecated in 2026-07-28 (SEP-2577): **sampling** (server asks the host's LLM for a completion), **roots** (server asks which directories it may touch), and **logging** (server pushes log lines). They still work during the deprecation window, but new servers should not adopt them. The last lesson explains why and what replaces each.

<Callout title="The one-line takeaway">
MCP servers cannot call the client — so when they need the user, they *return* a question (`InputRequiredResult`) and the client retries the same request with the answer; when they need time, they report progress or hand back a task handle. State rides in the request, never in the connection.
</Callout>
