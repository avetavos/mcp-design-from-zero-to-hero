## The client is the user's last line of defense

A server can be malicious, compromised, or simply buggy, and the model can be manipulated by text inside a tool result. The only party that acts for the user is the host. The specification therefore places concrete duties on clients and hosts. This lesson collects them; the [security module](/mcp/en/security-and-auth/) covers the server side and the OAuth details.

## Human in the loop

The tools specification is explicit: there should always be a human able to deny a tool invocation. Concretely, a host should:

- **Make visible which tools are exposed** to the model, per server.
- **Show a clear indicator when a tool is invoked.**
- **Show the inputs before calling the server**, so a manipulated model cannot exfiltrate data through arguments unnoticed.
- **Prompt for confirmation on sensitive operations.** Tool `annotations` (`destructiveHint`, `openWorldHint`) help you decide what counts as sensitive, but treat them as untrusted unless the server is trusted.

An automatic "always allow" for a server is a legitimate user choice. An automatic "always allow" that the user never made is a vulnerability.

## Treat everything from the server as data

Tool results, resource contents, prompt messages, tool descriptions, and annotations are all authored by the server. Any of them can contain text that reads like instructions. Rules:

- **Validate tool results** against `outputSchema` when one exists, and never dereference network `$ref` values in schemas by default.
- **Do not let descriptions or results change client behavior** directly. They go to the model as content, not to your code as commands.
- **Truncate and sanitize** before rendering; a result can be megabytes.
- **Log tool usage** — server, tool, arguments, outcome — for audit.
- **Implement timeouts** on every request.

## Elicitation UI rules

When a server asks for input, the client owns the interaction. The spec requires clients to:

- **Say which server is asking.** Never show an anonymous form.
- **Offer decline and cancel** at all times, and let the user review and edit form values before sending.
- **For URL mode:** display the full URL, highlight the domain, warn on suspicious or Punycode hosts, never pre-fetch the URL or its metadata, never open it without explicit consent, and open it in a way the client and model cannot inspect (a real browser or system view, not an embedded web view you control).
- **Never render URLs as clickable** in any elicitation field except the `url` of a URL-mode request.
- **Validate form responses** against the requested schema before sending them.

Form mode must never be used by a server to collect passwords or API keys; if you see such a request, that is a red flag about the server.

## Installing local servers safely

A stdio server is a program the host will execute with the user's privileges. If your host offers one-click installation from a config or a link, the spec says you **must** show a consent dialog first that:

- Displays the exact command, arguments included, without truncation.
- States plainly that it executes code on the user's machine.
- Requires explicit approval and allows cancel.

Beyond the minimum, good hosts highlight dangerous patterns (`sudo`, `rm -rf`, network calls, access outside expected directories), warn that servers run with the client's privileges, and launch servers in a sandbox with restricted filesystem and network access, granting more only on request. A server left listening on localhost over HTTP is reachable by any web page via DNS rebinding, which is why local servers should prefer stdio and remote ones must validate `Origin`.

## SSRF when talking OAuth

During authorization discovery the client fetches URLs a server hands it: the `resource_metadata` URL from `WWW-Authenticate`, the `authorization_servers` list, and the endpoints inside authorization-server metadata. A malicious server can point those at `http://169.254.169.254/` or `http://localhost:6379/`. Server-side hosts (an agent running in your cloud) must therefore:

- **Require HTTPS** for OAuth URLs outside loopback development.
- **Block private and reserved ranges** (`10/8`, `172.16/12`, `192.168/16`, `127/8`, `169.254/16`, `fc00::/7`, `fe80::/10`) — using a well-tested library, not a hand-written parser, because encoding tricks defeat naive checks.
- **Validate redirect targets** with the same rules, or disable automatic redirects.
- **Consider an egress proxy** that blocks internal destinations by policy.
- **Pin DNS between check and use** to defeat rebinding.

Also validate the metadata itself: the `issuer` in a fetched document must equal the issuer you built the well-known URL from, or discard it.

## Opening authorization URLs

The authorization URL comes from the server. A client **must** allow only `http://` (loopback only) and `https://` schemes and reject `javascript:`, `data:`, `file:`, `vbscript:` and friends — use an allowlist, not a blocklist. Never open a URL through a shell (`cmd.exe`, `sh`, PowerShell); use the platform's non-shell URL opener. In proxy architectures where a local service spawns stdio servers, an XSS in the client can escalate to code execution through that proxy, so these URL rules are part of your RCE defense, not just a browser nicety.

## Web clients: CSP

Browser-based hosts should ship a Content Security Policy: `default-src 'self'`, `script-src 'self'` (or a nonce for necessary inline scripts). It is the cheapest way to make a `javascript:` URL or an injected snippet from a server inert.

<Callout title="The one-line takeaway">
The client is the only party that acts for the user: keep a human able to deny every call, treat everything a server sends as data, own the elicitation UI, show the exact command before running a local server, and never fetch or open a server-supplied URL without scheme, range, and consent checks.
</Callout>
