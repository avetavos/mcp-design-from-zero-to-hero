## The problem: N apps × M integrations

Every AI application wants the same things: read the user's files, query a database, search an issue tracker, call an internal API. Before MCP, each application built each integration itself. Claude Desktop wrote a GitHub connector; VS Code wrote a GitHub connector; your in-house agent wrote a GitHub connector. Three apps, one API, three integrations — and the same again for every other data source.

That is the **N×M problem**: N applications times M data sources equals N×M bespoke adapters, every one of them slightly different, every one maintained by someone else.

The **Model Context Protocol (MCP)** replaces the grid with a standard. A data source implements the protocol once, as an **MCP server**. An application implements the protocol once, as an **MCP host**. After that, any host can talk to any server: N + M implementations instead of N×M.

## "USB-C for AI applications"

The usual analogy is USB-C. A laptop does not carry a bespoke port for every monitor, drive, and keyboard; it carries one standard port, and peripherals carry the matching plug. MCP is that port for AI applications: the host has one connector, and every context source — a database, a SaaS API, your local files — plugs into it.

The analogy holds in a second way. USB-C defines the plug and the negotiation, not what the device does. MCP defines the messages, the discovery, and the transport, not what your tools do or how the host uses the model. That deliberate scope is a strength: the protocol stays small, and everything domain-specific lives in your server.

## Where MCP sits next to the LLM API

MCP is **not** an LLM API. It does not send prompts to a model or stream tokens back. It sits beside the model API, feeding it context:

| Layer | Talks to | Examples |
|-------|----------|----------|
| LLM API | The model | Claude Messages API, tool-use loop |
| MCP host | MCP servers via MCP clients | Claude Desktop, Claude Code, VS Code, your agent |
| MCP servers | The outside world | Filesystem, GitHub, Sentry, your internal API |

A host asks its MCP servers what tools they offer, passes those tool definitions to the model, and when the model decides to call one, the host routes the call to the right server and hands the result back to the model. MCP covers the host↔server half of that loop. The host↔model half is the model provider's API.

## Who's who

- **Host** — the application the user is actually using. It owns the model, the UI, and the decision about what to expose to the model.
- **Client** — a component inside the host that holds one connection to one server. A host with three servers has three clients.
- **Server** — a program that exposes context: **tools** to act, **resources** to read, **prompts** to reuse. It can run as a subprocess on the user's machine or as a service on the internet.

## How this course is built

Every lesson starts from the **wire** — the JSON that actually crosses between client and server — and only then shows the SDK call that produces it. You will see the same server written in **TypeScript** (`@modelcontextprotocol/server`) and **Python** (`mcp`) side by side, in synced tabs. Pick your language once and it follows you through every lesson.

The course targets protocol revision **2026-07-28**, the current one. Where an older behaviour still matters for interoperability, it is called out explicitly as *legacy (2025-11-25 and earlier)* so you never confuse the two.

<Callout title="The one-line takeaway">
MCP turns the N×M integration grid into N + M by standardising how an AI application discovers and uses context: a host runs one client per server, and every server implements the same small protocol — leaving what the tools do, and how the host uses the model, entirely up to you.
</Callout>
