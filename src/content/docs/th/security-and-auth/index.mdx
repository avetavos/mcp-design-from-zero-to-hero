## ห้าฝ่าย สี่เส้นแบ่ง

ระบบ MCP ของจริงไม่เคยเป็นแค่ "client กับ server" request หนึ่งครั้งต้องข้าม trust boundary หลายชั้น และแต่ละชั้นคือจุดที่ credential อาจรั่ว ถูกเอาไปใช้ซ้ำ หรือถูกปลอมได้:

## stdio กับ HTTP authenticate ไม่เหมือนกัน

authorization spec ผูกกับ **transport** โดยรวมมันเป็น OPTIONAL และเมื่อ server รองรับ:

- **Streamable HTTP server SHOULD** implement OAuth 2.1 flow ตามที่อธิบายในโมดูลนี้
- **stdio server SHOULD NOT** implement มัน เพราะ stdio server คือ subprocess ที่ host รันขึ้นมาบนเครื่องของ user เอง มันรับ credential จาก environment (`env` ใน config ของ host, keychain, config file) เหมือน CLI ทั่วไป
- custom transport MUST ทำตามแนวปฏิบัติด้าน security ที่เป็นมาตรฐานของ protocol นั้น ๆ

เหตุผลตรงไปตรงมา: stdio server ไม่มี network endpoint ให้ต้องป้องกัน และ host ก็ตัดสินใจไว้แล้วว่าเชื่อใจมันพอที่จะรันมัน ส่วน remote HTTP server ใครก็ยิง POST ถึงได้ มันเลยต้องมีวิธีรู้ว่า *ใคร* กำลังถาม และ *ได้รับสิทธิ์อะไร* มาบ้าง

```json
// config ของ host สำหรับ stdio server: credential มาจาก environment
{
  "mcpServers": {
    "github": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@example/github-mcp"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}
```

## บทบาทตาม OAuth 2.1

MCP ไม่ได้คิดค้น authentication protocol ใหม่ แค่เอาบทบาทของ OAuth 2.1 มาแปะให้ผู้เล่นที่มีอยู่แล้ว:

| ฝ่ายใน MCP | บทบาท OAuth 2.1 | หน้าที่ |
|-----------------|----------------|----------------|
| MCP server (HTTP) | **Resource server** | รับ bearer token, ตรวจสอบ (signature, วันหมดอายุ, *audience*, scope) และตอบ `401`/`403` เมื่อไม่ผ่าน |
| MCP client | **OAuth client** | ค้นหา authorization server, ลงทะเบียนหรือระบุตัวตน, รัน authorization-code flow พร้อม PKCE แทน user แล้วส่ง token ไปกับทุก request |
| Authorization server | **Authorization server** | authenticate user, แสดงหน้า consent, ออก access token (และ refresh token ถ้ามี) *สำหรับ resource ที่ระบุ* |
| User | **Resource owner** | อนุญาตหรือปฏิเสธไม่ให้ client เข้าถึง server |

authorization server จะอยู่ข้าง ๆ MCP server หรือเป็น identity provider แยกต่างหากก็ได้ spec ตั้งใจไม่พูดถึงวิธี implement มันเลย แค่บังคับให้ MCP server *ชี้ไปหามัน* ผ่าน Protected Resource Metadata ซึ่งจะพูดถึงใน[บทถัดไป](/mcp/th/security-and-auth/oauth-flow/)

## สามเรื่องที่ spec เข้มงวดจริง ๆ

OAuth ส่วนใหญ่เป็น "SHOULD" แต่มีสามข้อที่เป็น "MUST" และเป็นข้อที่กัน token ไม่ให้เดินข้าม boundary ไปมั่ว ๆ:

1. **Audience binding** client ขอ token *สำหรับ server ตัวนี้* (พารามิเตอร์ `resource=`) และ server MUST ตรวจว่า token ถูกออกให้ตัวเองจริง token ของ `https://mail.example.com` ใช้กับ `https://mcp.example.com` ไม่ได้ แม้ authorization server ตัวเดียวกันจะเซ็นทั้งคู่ก็ตาม
2. **ห้าม token passthrough** server MUST NOT รับ token ที่ไม่ได้ออกให้ตัวเอง และ MUST NOT ส่งต่อ token ของ client ไปยัง downstream API ใด ๆ การเรียก upstream ต้องใช้ credential ของ server เอง
3. **Bearer header เท่านั้น** token เดินทางใน `Authorization: Bearer …` กับทุก request ห้ามใส่ใน query string ของ URL เพราะมันจะไปโผล่ใน log และ browser history

## มาตรฐานที่คุณจะได้เจอ

authorization spec ของ MCP ประกอบขึ้นจาก *ส่วนย่อย* ของงาน IETF และ OpenID ที่มีอยู่แล้ว ไม่ได้นิยาม crypto ใหม่ คุณไม่ต้องอ่านทั้งหมด แต่ควรจำชื่อได้:

| มาตรฐาน | MCP ใช้ทำอะไร |
|----------|----------------------|
| OAuth 2.1 (draft-ietf-oauth-v2-1) | flow พื้นฐาน: authorization code + PKCE ไม่มี implicit grant |
| RFC 6750 | การใช้ bearer token และรูปแบบ challenge ใน `WWW-Authenticate` |
| RFC 9728 | Protected Resource Metadata: วิธีที่ server ประกาศว่า authorization server ของตัวเองอยู่ที่ไหน |
| RFC 8414 | การค้นหา Authorization Server Metadata (`/.well-known/oauth-authorization-server`) |
| OpenID Connect Discovery 1.0 | discovery document อีกแบบ (`/.well-known/openid-configuration`) |
| RFC 8707 | Resource indicator: พารามิเตอร์ `resource=` ที่ผูก token เข้ากับ server หนึ่งตัว |
| RFC 9207 | พารามิเตอร์ `iss` ตอน redirect ที่ใช้กัน mix-up attack |
| Client ID Metadata Documents (draft) | ใช้ HTTPS URL เป็น client identifier แทน dynamic registration |
| RFC 7591 | Dynamic Client Registration ซึ่งตอนนี้ deprecated แล้ว แต่ยังเก็บไว้เพื่อ compatibility |
